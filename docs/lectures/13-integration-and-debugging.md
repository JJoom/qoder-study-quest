# 第 13 讲 · 前后端联调与调试

> 联调是前后端分离项目的必经关卡。本讲系统梳理联调问题的排查地图，并重点训练「把 AI 变成排错搭档」的提问方法。

## 1. 学习目标与本讲地图

学完本讲，你将能够：

- [ ] 用「五层排查法」定位任何前后端联调问题
- [ ] 熟练使用浏览器 Network 面板与后端日志做双向取证
- [ ] 掌握「给 AI 报障」的标准格式，一次说清问题
- [ ] 解决 CORS、401 循环、字段不一致三类高频联调问题
- [ ] 完成全链路回归走查

本讲地图：

```
排查方法论 → 给 AI 报障的格式 → 三类高频问题实战 → 全链路回归
```

## 2. 术语表

| 术语 | 一句话理解 |
| --- | --- |
| 联调 | 前后端各自开发完后，接在一起跑通的过程 |
| Network 面板 | 浏览器开发者工具里看所有 HTTP 请求的地方——联调第一现场 |
| 堆栈（Stack Trace） | 报错时程序打印的「案发过程记录」，从哪一层哪个方法抛出 |
| 预检请求（OPTIONS） | 浏览器在跨域请求前自动发的「问路」请求 |

## 3. 企业级知识点：五层排查法

任何联调问题，按请求经过的五层逐层排查，每层回答一个问题：

| 层 | 排查问题 | 取证工具 |
| --- | --- | --- |
| 1. 前端发没发 | Network 里有没有这个请求？参数对不对？ | 浏览器 Network |
| 2. 到达后端没有 | 后端日志有没有收到请求？没有→代理/端口/路径问题 | 后端控制台日志 |
| 3. 认证过了没 | 401？token 带了吗、过期了吗？ | Network 请求头 |
| 4. 逻辑对不对 | 进了 Controller/Service 但结果不对？ | 日志 + 断点 |
| 5. 响应解析对不对 | 后端返回正常但页面不显示？字段名对上了吗？ | Network 响应体 vs 前端代码 |

**纪律：从第 1 层往下查，不许跳层。** 90% 的「灵异问题」是第 1、2 层的低级失误（路径拼错、代理没配、忘了带 token）。

## 4. 分步实战

### 步骤 1：制造并侦破三个真实问题

本讲不设新代码任务，而是对现有系统做「故障演练」。请按下面流程亲手处理三类高频问题（如果没自然出现，可临时制造）：

#### 问题 A：接口 404

制造：把前端某请求路径改错一个字母（如 `/api/v1/prodcuts`）。

侦破流程演练：

1. Network 面板看到 404 → 确认是「请求路径」问题还是「后端没这个接口」
2. 复制完整报错信息给 AI：

> **给 AI 报障的标准格式（本讲核心技能）：**
>
> ```
> 【现象】商品列表页白屏，控制台无数据
> 【请求】GET /api/v1/prodcuts?page=1&size=10
> 【响应】HTTP 404，响应体 {"code":404,"message":"资源不存在","data":null}
> 【已排查】后端已启动且 /api/v1/products 正常返回数据
> 【相关代码】@src/api/product.js
> 请分析原因并给出修复。
> ```

**要点**：现象、请求、响应、已排查、相关代码——五要素齐全，AI 基本一轮命中；缺要素时 AI 只能反问或瞎猜。**这个格式适用于全课程剩余所有调试场景。**

#### 问题 B：401 死循环

制造：把后端 JWT 有效期临时改成 10 秒，登录后等过期再操作页面。

观察现象：页面反复跳登录页，或请求无限重试。

> **提示词示例：**
>
> ```
> 【现象】token 过期后页面反复跳转 /login，Network 里同一接口出现多次 401
> 【相关代码】@src/utils/request.js @src/router/index.js
> 请分析 401 处理链路中可能造成循环的原因并修复（例如：跳转前判断当前是否已在登录页、并发请求同时触发跳转）。
> ```

**检查要点**：修复后验证——过期后只跳一次登录页；多个并发请求同时 401 时不会抖动。

#### 问题 C：字段不一致

制造：把后端某个 VO 的字段 `mainImage` 临时改成 `imageUrl`，重启后端。

观察现象：页面图片不显示，但 Network 里响应是 200。

侦破：这就是五层法的第 5 层——**响应正常 ≠ 前端能用**。对照响应体 JSON 与前端使用的字段名，让 AI 统一修复（并强调以后端为准改前端，因为后端是契约方——或者反过来，关键是团队要定一个「谁改」的规矩）。

### 步骤 2：CORS 问题的正确姿势

虽然开发环境有 Vite 代理，生产或特殊场景仍会遇到 CORS。让 AI 讲透：

> **提示词示例：**
>
> ```
> 请解释：1）浏览器为什么有同源策略；2）OPTIONS 预检请求什么时候触发；
> 3）开发环境用代理 vs 后端配置 @CrossOrigin/全局 CORS 各自的适用场景；
> 4）为什么生产环境推荐用 Nginx 同源部署而不是开 CORS。
> ```

**检查要点**：如果 AI 建议你「在后端加 `@CrossOrigin("*")` 并且 allowCredentials=true」——这是无效且危险的组合，Spring 会直接报错。识别出来说明你真懂了。

### 步骤 3：让 AI 分析真实堆栈

从后端日志里找一段真实异常堆栈（例如访问不存在的订单），连同上下文贴给 AI：

> **提示词示例：**
>
> ```
> 后端抛出以下异常：
> 【粘贴完整堆栈】
> 触发操作：前端调用 GET /api/v1/orders/NO123
> 请定位抛出点、分析原因、给出修复建议，并说明如何在代码中防御。
> ```

**要点体会**：堆栈是最好的报障材料。练习从堆栈里找到「第一个属于 com.qshop 包的行」——那通常就是案发地点。

### 步骤 4：全链路回归走查

用一张表做结业回归，逐项打勾：

| 旅程 | 步骤 | 结果 |
| --- | --- | --- |
| 注册登录 | 注册 → 登录 → 刷新保持登录态 → 退出 | |
| 商品浏览 | 列表 → 搜索 → 分类筛选 → 分页 → 详情 | |
| 交易闭环 | 加购 → 改数量 → 结算 → 支付 → 订单已支付 | |
| 订单管理 | 下单不支付 → 取消 → 库存回补验证 | |
| 后台管理 | 商品增删改查 + 上传图片 + 上下架 + 用户启用禁用 | |
| 权限边界 | 普通用户访问 /admin 被拦截；接口 403 验证 | |

发现的每个问题，都用步骤 1 的「五要素报障格式」交给 AI 修复。

## 5. 常见坑与认知纠偏

1. **不看 Network 就问 AI**：先取证再报障。没有请求/响应证据的「它不工作」，AI 只能陪你猜。
2. **改代码凭感觉试**：每次只改一处、验证一次。同时改三处出了问题，你不知道是谁的锅。
3. **AI 修 bug 引入新 bug**：修复后必须回归原问题场景 + 相邻场景。本讲的回归表就是为此准备的。
4. **把环境问题当代码问题**：后端没启动、代理没生效、缓存没清——先排除环境因素。

## 6. 课后练习任务

1. 把「五要素报障格式」写成你自己的模板存进笔记，之后所有调试都按此格式
2. 故意制造一个「分页参数名不一致」的问题（后端 page/size，前端 pageNum/pageSize），用五层法侦破
3. 让 AI 总结本项目目前为止出现过的所有 bug（回顾你的对话历史），归类统计哪一层问题最多
4. Git 提交：`fix: 联调问题修复与回归`
