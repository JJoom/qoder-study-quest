# 第 14 讲 · 测试与代码质量

> 企业级项目与普通作业的分水岭：有测试、有评审。本讲让 AI 为核心业务写测试，体验 Qoder 的代码评审能力与社区热门 Skills。

## 1. 学习目标与本讲地图

学完本讲，你将能够：

- [ ] 说清单元测试与集成测试的分工
- [ ] 让 AI 为订单/库存核心逻辑生成高质量单元测试（含边界用例）
- [ ] 编写一个关键的并发回归测试并长期保留
- [ ] 使用代码评审（子 Agent / Skills）审查自己的代码
- [ ] 看懂测试报告，知道覆盖率的意义与局限

本讲地图：

```
测试策略 → 单元测试生成 → 并发回归测试 → 代码评审 → 覆盖率
```

## 2. 术语表

| 术语 | 一句话理解 |
| --- | --- |
| 单元测试 | 测试一个方法/类的行为，不依赖数据库和网络，毫秒级运行 |
| 集成测试 | 把组件接上真实依赖（数据库、Redis）一起测 |
| Mock | 用「假对象」替代真实依赖，例如假的 Mapper 返回预设数据 |
| 边界用例 | 测试输入的极端值：0、负数、刚好等于库存、空集合 |
| 测试覆盖率 | 有多少比例的代码被测试执行过——参考指标，不是目标 |
| 代码评审（Code Review） | 别人（或 AI）审查你的代码找问题，上线前的最后一道安检 |

## 3. 企业级知识点：测试金字塔与 AI 的分工

```
        ／＼        E2E 测试（端到端，贵而少）
       ／  ＼       集成测试（带数据库，适量）
      ／____＼      单元测试（多而快，主力）
```

课程策略：**单元测试覆盖核心业务规则**（状态机、库存扣减、金额计算），集成测试保证关键链路（登录、下单）可用。

AI 写测试的正确姿势：**你定测试什么（用例清单），AI 负责怎么写（代码实现）**。直接说「给订单服务写测试」得到的往往是平庸用例；先列用例清单再让它实现，质量完全不同。

## 4. 分步实战

### 步骤 1：为订单状态机写单元测试

先自己列用例清单，再交给 AI：

> **提示词示例：**
>
> ```
> @modules/order 的状态流转代码 请为订单状态机编写 JUnit 5 + Mockito 单元测试，用例清单：
> 1. UNPAID 订单支付成功 → 状态 PAID
> 2. UNPAID 订单取消 → 状态 CANCELLED 且库存回补被调用
> 3. PAID 订单再次支付 → 抛出 ORDER_STATUS_INVALID（错误码 10002）
> 4. CANCELLED 订单支付/取消 → 均拒绝
> 5. 不存在的订单 → 抛出 404 类异常
> Mapper 用 Mockito 模拟，不连数据库。
> ```

**预期产出**：`OrderServiceTest`（或状态机组件的测试）。

**验证**：

```powershell
mvn test -Dtest=OrderServiceTest
```

**检查要点**：

- 断言是否具体（断言状态值与异常码，而不是只断言「没抛异常」）
- 有没有「永远通过」的假测试（空断言、断言常量）——这是 AI 生成测试最常见的质量问题

### 步骤 2：为库存扣减写测试（含边界）

> **提示词示例：**
>
> ```
> 为库存扣减逻辑写单元测试，重点覆盖边界：
> 1. 库存充足扣减成功；2. 购买数量 = 库存（刚好买空）成功；
> 3. 购买数量 = 库存+1 → 抛 STOCK_NOT_ENOUGH；4. 库存为 0 → 拒绝；
> 5. 模拟 version 冲突（更新影响行数=0）→ 抛库存不足
> ```

**检查要点**：「刚好买空」这个边界最容易被 AI 漏掉——检查用例 2 是否存在。

### 步骤 3：保留并发回归测试

把第 10 讲的并发超卖测试整理为正式测试类 `StockConcurrencyTest`，长期留在项目里：

> **提示词示例：**
>
> ```
> 把之前的并发下单测试整理为正式集成测试 StockConcurrencyTest：
> 使用 @SpringBootTest 连真实本地库，20 线程抢 10 库存，断言库存不为负。
> 加注释说明：这是防超卖回归测试，任何人改动下单链路必须先跑它。
> ```

**意义**：这个测试就是项目的「质量护栏」——以后让 AI 重构下单逻辑时，先跑它，绿了才算改完。

### 步骤 4：代码评审——使用子 Agent 与社区 Skills

两种评审方式都体验一遍：

**方式一：代码评审子 Agent**。在 Qoder 中发起代码评审（CodeReview 子 Agent），范围选择本讲之前的全部改动。

**方式二：社区热门 Skills**。使用 find-skills 搜索代码评审/提交类技能（例如 commit 规范类技能），安装一个体验：

> **操作示例**：在对话中询问「帮我找一个规范化 git 提交的 skill」，按引导安装后用它生成一次规范的提交信息。

**对评审结果的处理纪律**：

1. 逐条看 AI 评审意见，判断「真问题 / 误报 / 风格偏好」
2. 真问题立即修；误报记录下来（可补充进 Rules 防止再次误报）
3. **不要因为「AI 说没问题」就跳过自己的审查**——评审 AI 也会漏

**检查要点**：让评审重点看第 07-10 讲的安全相关代码（放行清单、越权校验、事务边界），对照你当时的手动审查结果，看 AI 有没有发现你漏掉的。

### 步骤 5：看一眼覆盖率

> **提示词示例：**
>
> ```
> 为项目接入 JaCoCo 测试覆盖率插件，运行测试后告诉我哪些核心类覆盖率低于 60%。
> ```

**正确解读**：覆盖率低不代表代码烂，覆盖率高也不代表没 bug。关注「核心业务类」（order/payment/product service）的覆盖率，而不是追数字。

## 5. 常见坑与 AI 幻觉识别

1. **假测试**：断言恒真（`assertTrue(true)`）、测试方法体为空、只测 happy path。逐个打开测试读断言。
2. **Mock 过度**：把被测对象本身也 Mock 了——测试等于没测。检查 `@Mock` 的只有依赖，被测类是真实实例。
3. **测试与实现同源错误**：AI 写实现时理解错了需求，写测试时会把同样的错误「固化」进断言。**先自己确认预期行为，再核对断言是否符合你的预期**——测试是照妖镜，不是生成器。
4. **并发测试不稳定**：线程数/时序导致偶发失败。要求 AI 用 CountDownLatch 等机制保证线程同时起跑。

## 6. 课后练习任务

1. 为金额计算写测试：订单总价 = Σ(单价 × 数量)，构造 0.1 + 0.2 类精度场景验证 BigDecimal 正确性
2. 为登录流程写一个集成测试（@SpringBootTest + MockMvc）：注册 → 登录 → 带 token 访问受保护接口
3. 把评审发现的 1-2 个真问题修复，并更新对应 spec 文档
4. 思考题：哪些 bug 是测试测不出来的？（提示：需求理解错误、UI 体验）写下你的答案
5. Git 提交：`test: 核心业务测试与评审修复`
