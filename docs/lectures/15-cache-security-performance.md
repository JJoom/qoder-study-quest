# 第 15 讲 · 缓存、安全与性能

> 本讲为 QShop 补上企业级的最后三块拼图：Redis 缓存热点数据、安全漏洞系统排查、SQL 与接口性能优化。

## 1. 学习目标与本讲地图

学完本讲，你将能够：

- [ ] 为商品详情实现 Redis 缓存并正确处理「更新时失效」
- [ ] 说清缓存三大经典问题（穿透/击穿/雪崩）及课程采用的对策
- [ ] 按安全清单系统排查注入、XSS、越权风险
- [ ] 用 Explain 分析慢 SQL 并让 AI 给出优化方案
- [ ] 建立「先测量后优化」的性能工作习惯

本讲地图：

```
缓存实现 → 缓存失效策略 → 安全排查清单 → SQL 优化 → 性能验证
```

## 2. 术语表

| 术语 | 一句话理解 |
| --- | --- |
| 缓存 | 把常读的数据放内存（Redis），下次直接从内存拿，不打扰数据库 |
| 缓存穿透 | 查询根本不存在的数据，缓存永远 miss，请求全打到数据库 |
| 缓存击穿 | 热点 key 过期的一瞬间，海量请求同时打到数据库 |
| 缓存雪崩 | 大量 key 同时过期，数据库瞬间被压垮 |
| XSS | 攻击者把恶意脚本塞进页面（如商品名里藏 `<script>`），在别人的浏览器里执行 |
| SQL 注入 | 攻击者把 SQL 片段拼进查询参数，篡改你的 SQL 语义 |
| 越权 | 看到了/改了不该自己操作的数据（分水平越权与垂直越权） |
| Explain | MySQL 的 SQL 体检命令：展示这条查询走没走索引、扫了多少行 |

## 3. 分步实战

### 步骤 1：商品详情缓存

> **提示词示例：**
>
> ```
> @modules/product 为商品详情实现 Redis 缓存：
> 1. GET /api/v1/products/{id}：先查 Redis（key: product:detail:{id}，JSON 序列化），
>    未命中查库并写回缓存，TTL 30 分钟 + 随机偏移（0-5 分钟）
> 2. 管理端修改/删除/上下架商品时，删除对应缓存 key
> 3. 商品不存在时缓存空标记（TTL 2 分钟）防穿透
> ```

**预期产出**：带缓存的商品详情链路。

**验证**：

1. 第一次请求详情 → 后端日志有 SQL；立即第二次请求 → 无 SQL
2. `redis-cli TTL product:detail:1` 查看过期时间
3. 管理端修改商品 → 再查详情是最新数据（缓存已失效）

**检查要点**：

- 「随机 TTL 偏移」确实实现了（防雪崩的最小成本方案）——抽查两个 key 的 TTL 不同
- 所有写操作分支（修改、删除、上下架）都有缓存失效，漏一个就是数据不一致 bug

**三大问题的课程级对策小结**：

| 问题 | 课程对策 | 企业进阶方案（了解即可） |
| --- | --- | --- |
| 穿透 | 空值缓存 2 分钟 | 布隆过滤器 |
| 击穿 | 单体低并发可接受；详情 TTL 错开 | 互斥锁重建缓存 |
| 雪崩 | TTL 随机偏移 | 多级缓存、限流降级 |

### 步骤 2：安全排查清单（逐项实测）

让 AI 陪你做攻防演练，每一项都要实测出结论：

> **提示词示例：**
>
> ```
> 请以安全工程师身份对 QShop 做排查，对每一项给出：风险点位置、验证方法、结论。
> 1. SQL 注入：搜索关键字传 "1' OR '1'='1" 与 "%; DROP TABLE"，检查 Mapper 全部为参数绑定
> 2. XSS：创建商品名为 <script>alert(1)</script> 的商品，前端展示处确认被转义
> 3. 水平越权：用户 A 的 token 访问用户 B 的订单号/地址 id
> 4. 垂直越权：普通用户 token 调用全部 /api/v1/admin/** 接口
> 5. 敏感信息：全局搜索日志代码，确认没有打印密码/token；检查响应里没带 password 字段
> 6. 认证缺陷：篡改 JWT 载荷（不重签名）请求，确认被 401 拒绝
> ```

**预期产出**：逐项排查报告 + 发现的真实问题修复。

**检查要点**：

- XSS 防护依赖 Vue 的默认转义——**只要哪里用了 v-html，哪里就是风险点**，全局搜索 `v-html` 确认没有或已有净化
- 排查报告不能只看 AI 结论：第 3、4 项必须自己用 HTTP 工具（第 06 讲教过）实测一次

### 步骤 3：SQL 性能体检

> **提示词示例：**
>
> ```
> 请给出本项目最关键的 5 条查询 SQL（商品列表、订单列表、订单详情等），
> 对每条给出 EXPLAIN 分析方法：如何看 type、key、rows 三列判断是否走了索引。
> ```

然后对商品列表查询实测：

```sql
EXPLAIN SELECT * FROM product
WHERE deleted = 0 AND status = 'ON_SALE' AND category_id = 1
ORDER BY created_at DESC LIMIT 0, 10;
```

**判读口诀**：`type` 至少要到 range/ref（ALL 是全表扫描，危险信号）；`key` 非空说明走了索引；`rows` 越小越好。

**检查要点**：如果 AI 建议加「组合索引」，让它说明索引列顺序的理由（等值条件在前、范围/排序在后），而不是照单全收。

### 步骤 4：性能验证——先测量后优化

> **提示词示例：**
>
> ```
> 写一个简单的压测脚本（JMeter 说明或 Java/PowerShell 循环请求均可）：
> 对 GET /api/v1/products/{id} 连续请求 200 次，统计加缓存前后的平均耗时对比。
> ```

**预期产出**：一组对比数据（缓存命中后耗时通常下降一个数量级）。

**要点体会**：优化必须用数字说话。「感觉变快了」不是企业级工作方式——这也是向 AI 描述性能需求时该有的习惯：给指标，不给形容词。

## 4. 常见坑与 AI 幻觉识别

1. **缓存与数据库不一致**：最常见的错是「先更库后删缓存」写成「只更库不删缓存」。审查所有商品写路径的缓存失效调用。
2. **序列化幻觉**：AI 可能混用 JSON 字符串和 Java 序列化存 Redis，读的时候类型对不上。统一 JSON + 明确的反序列化类型。
3. **安全排查走过场**：AI 的排查报告可能全是「未发现问题」。对高风险项（越权）坚持自己实测取证。
4. **盲目加索引**：每个索引建议都问「这条索引服务哪条查询」，答不出来就不加。
