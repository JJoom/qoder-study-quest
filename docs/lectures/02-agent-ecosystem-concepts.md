# 第 02 讲 · Agent 生态概念扫盲（零基础版）

> 本讲一次性讲透你在 AI 编程圈会听到的所有名词：Agent、上下文、Rules、MCP、Skills、子 Agent、Harness。全部用生活类比解释，每个概念配一个 5 分钟内可上手的小练习。

## 1. 学习目标与本讲地图

学完本讲，你将能够：

- [ ] 说清 Agent 和普通 AI 问答的区别
- [ ] 理解「上下文」是什么，会用 @ 给 AI 提供上下文
- [ ] 知道 Rules、MCP、Skills、子 Agent、Harness 分别解决什么问题
- [ ] 在 Qoder 中完成上述每个概念的最小体验练习

本讲地图：

```
Agent（会动手的 AI） → 上下文（AI 的工作记忆） → Rules（给 AI 定家规）
→ MCP（万能插头） → Skills（固定招式） → 子 Agent（派给专人） → Harness（驾驭框架）
```

## 2. 术语表

| 术语 | 一句话理解 |
| --- | --- |
| Agent（智能体） | 不只动嘴回答问题，还会**自己动手**：读文件、改代码、跑命令的 AI |
| 上下文（Context） | AI 回答问题时「看得见」的全部信息，相当于它的工作记忆 |
| Rules（规则） | 你预先给 AI 定的「家规」，每次对话自动生效，无需重复叮嘱 |
| MCP（Model Context Protocol） | 给 AI 装的「万能插头」标准，让它能调用外部工具和数据源 |
| Skills（技能） | 把某类任务的做法写成「招式说明书」，AI 遇到匹配场景就照章办事 |
| 子 Agent（Subagent） | 主 AI 把子任务派给「专职分身」去做，各司其职 |
| Harness（驾驭框架） | 承载和驾驭 AI 的工具框架——IDE 就是 harness，Qoder 本身即是一个 |

## 3. 概念逐个讲透

### 3.1 Agent：从「动嘴」到「动手」

**类比**：上一讲你用的「问答」，像电话咨询专家——他告诉你怎么做，但活还得你自己干。**Agent 像请了位驻场工程师**——你交代任务，他自己打开文件、修改代码、运行命令、看到报错再自己修，直到任务完成。

两者的核心区别：

| | 普通问答 | Agent |
| --- | --- | --- |
| 能否读写文件 | 只能给建议 | 能直接改你的项目文件 |
| 能否执行命令 | 不能 | 能在终端执行命令 |
| 典型任务 | 「这段代码什么意思」 | 「给项目加一个用户注册接口并保证能跑通」 |

**关键认知**：Agent 动手能力强，所以**你更要盯紧它干了什么**。Qoder 在执行文件修改、运行命令时通常会展示动作并征求确认——不要无脑放行，重要操作先看一眼。

> **5 分钟练习**：在 Qoder 对话中让 AI 以 Agent 方式完成一件事：「帮我创建一个 notes.md 文件，写入今天的学习主题：Agent 初体验」。观察它展示的动作流程和确认环节。

### 3.2 上下文：AI 的工作记忆

**类比**：AI 回答问题时，就像开卷考试——它能参考的「开卷资料」就是上下文。**资料里没有的，它只能靠猜**。

上下文包括：你当前发的消息、本次对话的历史、你主动提供的文件内容、以及 IDE 自动附带的项目信息。

最实用的主动提供上下文方式：**@ 引用**。在对话输入框输入 `@`，可以选择把某个文件、文件夹「附」给 AI。

**为什么重要**：企业项目里 AI 最容易犯的错就是「不知道项目已有的约定」。比如你说「写一个分页接口」，AI 不知道你项目的分页参数叫 `page/size` 还是 `pageNum/pageSize`——把相关文件 @ 给它，它就照着写了。

> **5 分钟练习**：把上一讲的 `hello.py` 通过 @ 引用提供给 AI，问：「@hello.py 这个程序如果用户输入数字会怎样？帮我加一个输入校验」。体会「AI 确实读到了文件内容」的感觉。

**何时开新会话（企业级实操重点）**：上下文不是越大越好，三种情况建议另起新会话：

1. **任务切换**：从「写后端接口」切到「调前端页面」时，旧对话的历史只会干扰新任务
2. **对话过长导致 AI 忘事**：发现 AI 开始忘记早先的约定、重复犯已纠正过的错，说明上下文被稀释了
3. **被错误方向带偏**：AI 沿着错误思路越走越远时，与其在旧会话里拉回来，不如新开会话重新交代

新会话的代价是上下文清零，所以开新会话时要把关键文件重新 @ 给它，并用两三句话把背景交代清楚。

**补充认识：Repo Wiki**。Qoder 能自动为项目生成一份「项目知识库」（Repo Wiki），把代码结构、模块职责整理成可浏览的文档；你可以在 Qoder 界面中找到它的入口。当你想快速了解一个陌生项目（或让 AI 基于全局理解回答架构问题）时非常有用。

### 3.3 Rules：给 AI 定的家规

**类比**：你每次给新同事交代任务都要重复「我们代码用 4 空格缩进、日志必须用 slf4j、接口路径以 /api/v1 开头……」——烦不烦？Rules 就是把这些话写成一张「贴在墙上的团队守则」，AI 每次干活前自动读一遍。

Rules 的典型内容：

- 编码规范（命名、缩进、注释语言）
- 项目约定（分层结构、统一响应体格式、错误码规则）
- 行为约束（「修改代码前先说明方案」「不要引入新的依赖，除非我确认」）

**价值**：Rules 是把「口头叮嘱」沉淀为「制度」。第 04 讲我们会为 QShop 项目写真正的 Rules。

> **5 分钟练习**：在项目根目录创建 `.qoder/rules/` 目录（如你的版本支持通过设置界面创建 Rules，用界面操作代替），新建一个规则文件写入：「所有回复使用中文；生成 Python 代码时函数必须带 docstring」。然后让 AI 写一个小函数，观察它是否自动遵守。

### 3.4 MCP：给 AI 装的万能插头

**类比**：AI 默认只会「读文本、写文本」。但真实开发中你希望它能查数据库、操作浏览器、调用公司内部系统。MCP（Model Context Protocol）就是一套**标准化的插头/插座协议**：第三方把工具做成「插头」（MCP Server），AI 工具这边提供「插座」，插上就能用。

举例（本课程后续会间接用到）：

- 浏览器 MCP：让 AI 打开网页、点击按钮、截图——可用于自动测试前端页面
- 数据库 MCP：让 AI 直接查询数据库结构辅助建表

**零基础阶段你只需要知道**：MCP = 扩展 AI 能力边界的标准化方式；Qoder 支持配置 MCP；课程第 16 讲的进阶路线会告诉你何时需要它。

### 3.5 Skills：教 AI 的固定招式

**类比**：Rules 是「价值观层面的家规」，Skills 是「具体招式的说明书」。比如「部署到 Vercel」这件事有固定流程（装 CLI → 登录 → 构建 → 部署），把它写成一份 Skill，AI 遇到部署需求就照着说明书一步步执行，不会每次现场发挥。

Skills 的本质是**可复用的任务操作手册**（通常是 Markdown 文件，描述何时使用、执行步骤）。Qoder 内置和社区提供了不少现成 Skills，你后面课程会用到几个热门的，第 16 讲还会介绍如何自己写。

### 3.6 子 Agent：把任务派给专人

**类比**：主 Agent 像项目经理，遇到「代码评审」这种专业活，可以派给「评审专员」（CodeReview 子 Agent）；遇到「要上网操作」的活，派给「浏览器专员」。每个子 Agent 有自己专注的领域和工具集，干完把结果汇报回来。

**好处**：专业的事交给专业的分身；主对话保持清爽，不会被大量中间细节淹没。

**零基础阶段你只需要知道**：Qoder 中有现成的子 Agent（如代码评审），到第 14 讲做代码评审时你会实际用到。

### 3.7 Harness：驾驭 AI 的工具框架

**类比**：AI 模型像一台发动机，光有发动机不能上路——需要车架、方向盘、刹车、仪表盘。**Harness 就是把发动机装成整车的框架**：它负责管理对话、调度工具调用、控制权限、展示结果。

你在网上看到的 harness 一词，指的就是这类「AI 驾驭框架」。Qoder 本身就是一个 harness——它把大模型、文件操作、终端、上下文管理等组装成你能直接使用的 IDE。后面提到的 OpenSpec，则是跑在 harness 之上的「流程工具包」。

### 3.8 加餐：好提示词的六要素（全课程提示词速查卡）

概念都认识了，最后把「怎么对 AI 说话」沉淀成一张速查卡。一个好提示词通常包含六个要素：

| 要素 | 含义 | 例子 |
| --- | --- | --- |
| 角色 | 让 AI 以什么身份思考 | 「请以资深 DBA 身份……」 |
| 上下文 | 用 @ 引用相关文件/规格 | 「@schema.sql @modules/category」 |
| 目标 | 一句话说清要做什么 | 「实现商品列表分页接口」 |
| 约束 | 边界条件与技术限制 | 「参照样板风格；金额用 BigDecimal；禁止拼接 SQL」 |
| 输出格式 | 期望产出的形态 | 「先给设计思路，我确认后再写代码」 |
| 验证标准 | 怎么算做完了 | 「访问 /api/v1/products 返回分页结构即通过」 |

对照示例：

> **烂提示词**：写个商品接口。
>
> **好提示词**：@db/schema.sql @modules/category 请以样板模块的风格实现商品列表接口：GET /api/v1/products，支持 page/size/categoryId/keyword 参数，只返回上架商品；金额用 BigDecimal；先给我接口设计思路，确认后再写代码；完成后告诉我如何用 HTTP 工具验证。

六要素不必每次全写（小任务可以省），但缺得越多，AI 的发挥越随机。**本课程后续所有提示词示例都是按这个结构编写的**，你可以对照体会每个要素的作用。

## 5. 常见坑与认知纠偏

1. **「Agent 会不会乱删我的东西？」**——正规 harness 的危险操作（删文件、高风险命令）都会先征求确认或受限。但建议重要工作保持 Git 提交习惯，随时可回滚（第 04 讲建立）。
2. **「上下文是不是越大越好？」**——不是。上下文越杂，AI 注意力越分散。只提供与任务相关的文件，这是企业级 AI 开发的基本功。
3. **「Rules 写了就万事大吉？」**——Rules 提高一致性但不保证 100% 遵守，审查环节永远不能省。
