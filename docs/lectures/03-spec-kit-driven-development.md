# 第 03 讲 · Spec 驱动开发与 Spec Kit 实战

> 本讲是全课程最重要的方法论一讲：学会「先写清楚要什么，再让 AI 动手」。我们将使用 GitHub 官方开源工具 Spec Kit 完成第一次完整的 Spec 驱动开发演练。

## 1. 学习目标与本讲地图

学完本讲，你将能够：

- [ ] 解释为什么「一句话需求直接让 AI 写代码」会翻车
- [ ] 说出 Spec 驱动开发（SDD）的核心理念
- [ ] 安装并初始化 Spec Kit
- [ ] 完整走一遍 constitution → specify → plan → tasks → implement 五阶段流程
- [ ] 看懂每个阶段产出的 Markdown 工件的作用

本讲地图：

```
翻车案例 → SDD 理念 → 安装 Spec Kit → 五阶段实战演练 → Plan Mode 对比
```

## 2. 术语表

| 术语 | 一句话理解 |
| --- | --- |
| Spec（规格/规格书） | 用文档把「要做什么、做成什么样」写清楚，是需求的标准答案 |
| SDD（Spec-Driven Development，Spec 驱动开发） | 先写规格、再出方案、再拆任务、最后实现的开发流程 |
| Spec Kit | GitHub 开源的 SDD 工具包，给 AI 编码助手提供现成的五阶段流程模板 |
| constitution（项目宪法） | 项目的不可逾越原则：技术底线、质量标准、做事规矩 |
| specify | 动词/阶段名：编写需求规格书 |
| plan | 阶段名：根据规格制定技术实现方案 |
| tasks | 阶段名：把方案拆成一个个可执行的小任务 |
| implement | 阶段名：按任务清单逐个实现代码 |
| 工件（Artifact） | 流程产出的文档文件（本讲里都是 Markdown），作为下一阶段的输入 |
| Plan Mode（计划模式） | Qoder 内置功能：AI 先出实施方案，你确认后才动手改代码 |

## 3. 为什么需要 Spec 驱动开发：一个翻车案例

假设你对 AI 说：

> 「帮我写一个电商网站的购物车功能。」

AI 会立刻开始写代码。但它不得不自己猜：

- 购物车存数据库还是 Redis？
- 游客能不能加购？
- 商品下架了购物车里怎么处理？
- 数量上限多少？价格为 0 的赠品怎么算？

每个它猜的地方，都是未来返工的地方。更糟的是：**代码已经写了一大堆，你想改方向只能推翻重来**。这就是「vibe coding（凭感觉写代码）」的典型结局——小玩具没问题，企业级项目必翻车。

**SDD 的解法**：把「猜」的环节前置成「写清楚」。在写代码之前，先用结构化文档锁定需求、方案和任务。文档一旦确定，AI 每次实现都有据可依，你审查也有据可查。

**一句话记忆：代码是最贵的产出，所以要让最便宜的产出（文档）先跑在前面。**

## 4. Qoder 能力点讲解

本讲用到的 Qoder 能力：

| 能力 | 用途 |
| --- | --- |
| 内置终端 | 执行 `uv`、`specify` 命令 |
| Agent 对话 | 执行各阶段的 spec 命令、审查和修改生成的文档 |
| 文件浏览 | 查看 Spec Kit 生成的 `.specify/` 目录和 Markdown 工件 |
| Plan Mode | 作为 SDD 的轻量补充（第 7 节介绍） |

## 5. 安装 Spec Kit

### 5.1 前置条件

- Python 3.11+（验证：终端执行 `python --version`）
- uv（Python 包管理工具）

安装 uv（PowerShell）：

```powershell
powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"
```

安装完成后**重新打开终端**，验证：

```powershell
uv --version
```

### 5.2 安装 Spec Kit CLI

```powershell
uv tool install specify-cli
```

验证：

```powershell
specify --help
```

> 提示：若提示命令不存在，关闭并重开终端，让 PATH 生效。

### 5.3 初始化演练项目

本讲用一个小型演练项目走完整流程：**命令行待办清单（Todo CLI）**——麻雀虽小五脏俱全。

```powershell
mkdir sdd-demo
cd sdd-demo
specify init . --ai qoder
```

> 说明：`--ai` 指定与你使用的 AI 工具集成。若你的 Spec Kit 版本没有 `qoder` 选项，使用 `--ai generic`（通用集成，适配任何工具）。初始化完成后查看生成的目录结构，重点是 `.specify/` 目录（存放模板与脚本）和各阶段的命令文件。

初始化成功后，你会在项目中看到类似结构：

```
sdd-demo/
├── .specify/            # Spec Kit 的模板、脚本、记忆目录
│   ├── templates/       # 各阶段文档模板
│   └── memory/          # constitution.md 将生成在这里
└── specs/               # 各功能的规格/计划/任务文档将生成在这里（首个功能执行 specify 时创建）
```

## 6. 五阶段实战演练：Todo CLI

下面每个阶段给出「你在 AI 对话里输入的指令示例」「预期产出」「检查要点」。

### 阶段 1：constitution——立项目宪法

宪法定义项目不可逾越的原则。在 AI 对话中输入：

> **指令示例：**
>
> ```
> /constitution 为这个命令行待办清单项目制定宪法。核心原则：
> 1. Python 3.11+，不引入 Web 框架，只做命令行工具
> 2. 数据持久化用本地 JSON 文件，不引入数据库
> 3. 所有对外函数必须有单元测试
> 4. 代码注释与文档使用中文
> 5. 任何破坏数据文件兼容性的改动必须向后兼容
> ```

**预期产出**：`.specify/memory/constitution.md` 文件，包含你列出的原则及少量扩展说明。

**检查要点**：

- 通读宪法，确认没有被 AI「加戏」加进你不认可的原则
- 宪法宁少勿多：只写真正不可妥协的原则

### 阶段 2：specify——写需求规格

> **指令示例：**
>
> ```
> /specify 我要开发一个命令行待办清单工具，用户故事如下：
> 1. 作为用户，我可以添加待办事项（带标题，可选截止日期）
> 2. 作为用户，我可以查看待办列表，区分"未完成/已完成/已过期"
> 3. 作为用户，我可以把某个待办标记为完成
> 4. 作为用户，我可以删除待办事项
> 5. 作为用户，我可以按截止日期或创建时间排序
> 注意：本阶段只写"做什么"，不要涉及技术实现细节。
> ```

**预期产出**：`specs/001-xxx/spec.md`，内容是结构化的需求描述（用户故事、验收标准、边界条件），**不含技术选型**。

**检查要点（重要）**：

- 逐条对照你的原始需求，看有没有漏项或被曲解的地方
- 重点看 AI 补充的边界条件（例如：标题为空怎么办？截止日期已过还能标记完成吗？），这些「被提前问出来的问题」正是 SDD 的价值所在
- 有不满意的地方直接让 AI 修改：「验收标准 3 补充：标记完成时记录完成时间」

### 阶段 3：plan——制定技术方案

> **指令示例：**
>
> ```
> /plan 技术栈约束：Python 3.11+ 标准库为主，参数解析用 argparse，数据存 data/todos.json。请基于 spec.md 制定实现计划。
> ```

**预期产出**：`specs/001-xxx/plan.md`（技术方案）以及配套的技术上下文文档，内容包括技术选型、数据模型设计、项目结构、与宪法的一致性检查结论。

**检查要点**：

- 方案是否与宪法冲突（例如 AI 提议引入 SQLite 就违反宪法，必须驳回）
- 数据结构设计是否合理（待办事项有哪些字段、JSON 文件长什么样）
- 这个阶段是你「花小钱办大事」的最后机会：改文档比改代码便宜得多

### 阶段 4：tasks——拆分任务

> **指令示例：**
>
> ```
> /tasks 请基于 plan 拆分为可逐个实现和验证的任务清单。
> ```

**预期产出**：`specs/001-xxx/tasks.md`——一份编号任务清单，例如：

```
- T001 搭建项目骨架与数据文件读写模块
- T002 实现"添加待办"命令 add
- T003 实现"查看列表"命令 list（含排序与状态区分）
- T004 实现"标记完成"命令 done
- T005 实现"删除"命令 remove
- T006 补充单元测试与边界场景
```

**检查要点**：

- 每个任务是否足够小（一个任务对应一次 AI 实现 + 一次验证）
- 任务顺序是否合理（先数据层后命令层）

### 阶段 5：implement——逐任务实现

> **指令示例（先只做第一个任务）：**
>
> ```
> /implement 请实现 T001。
> ```

**预期产出**：AI 按照 tasks.md 中 T001 的描述生成代码，并更新 tasks.md 中该任务的状态。

**检查要点与工作节奏（本讲最重要的习惯）**：

1. **一次只做一个任务**，做完运行验证（`python todo.py add "学习 Spec Kit"`）通过后再做下一个
2. 发现实现与 spec 不符时，不是随口让 AI 改代码，而是先判断：是代码错了（改代码），还是 spec 想错了（改 spec 再改代码）
3. 全部任务完成后，对照 spec.md 的验收标准逐条验收

至此，你完整走完了一次 Spec 驱动开发闭环：

```
constitution（宪法）→ specify（规格）→ plan（方案）→ tasks（任务）→ implement（实现）
     原则               做什么          怎么做         分成几步         一步步做
```

## 7. Qoder Plan Mode：轻量版的「先方案后施工」

Spec Kit 适合完整功能的正式流程；日常小改动不必每次都走五阶段。Qoder 的 Plan Mode 是轻量补充：

- 开启 Plan Mode 后，AI **只出实施方案、不动代码**
- 你审查方案、提出修改，确认后才开始施工
- 适合「改一个功能」「重构一个类」这类中等规模任务

**选择建议**：

| 场景 | 用什么 |
| --- | --- |
| 新功能模块、跨多文件的复杂改动 | Spec Kit 完整流程 |
| 单点功能修改、小重构 | Plan Mode |
| 改个文案、修个明显小 bug | 直接对话 |

> **练习**：切到 Plan Mode，对演练项目提一个需求「增加 /stats 命令，统计各状态待办数量」，观察 AI 先出方案、待你确认的流程。

## 8. 常见坑与 AI 幻觉识别

1. **AI 生成的规格比你想象的「详细」，但可能是编的**。规格里出现的每个业务规则，都要问自己：这是我想要的，还是 AI 脑补的？例如 AI 可能自行规定「待办标题最长 50 字」——可以接受，但要过目。
2. **plan 阶段偷偷违反宪法**。检查 plan 与 constitution 的一致性结论，别只看结论，抽查关键选型。
3. **任务粒度过大**。如果某个 task 描述超过 5 行，让 AI 继续拆分。
4. **implement 时脱离 spec 自由发挥**。发现 AI 实现了 spec 里没有的功能，要求它删除——范围蔓延是企业项目失控的常见原因。

## 9. 课后练习任务

1. 继续完成 Todo CLI 的 T002-T006，体验「逐任务实现 + 逐任务验证」的节奏
2. 中途故意修改一次需求（例如给 add 命令加优先级参数）：先改 spec.md，再改 plan/tasks，最后改代码——体会「文档先行」的修改流程
3. 用 Plan Mode 完成一个小功能，对比它与 Spec Kit 流程的轻重差异
4. 写下你的体会：五阶段中，哪个阶段的产出对代码质量影响最大？参考答案：specify 阶段——需求错了，后面方案、任务、代码全部跟着错，而且越晚发现返工成本越高；这正是「代码最贵、文档先行」的原因
