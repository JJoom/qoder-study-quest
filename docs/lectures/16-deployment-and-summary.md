## 2. 术语表

| 术语 | 一句话理解 |
| --- | --- |
| Docker / 容器 | 把应用连同运行环境打包成「集装箱」，到哪台机器都能原样跑起来 |
| 镜像（Image） | 集装箱的图纸；容器是按图纸跑起来的实例 |
| Dockerfile | 写「怎么打包」的配方文件 |
| Nginx | 高性能 Web 服务器：对外发页面、对内把 /api 转发给后端 |
| 反向代理 | 用户以为在跟 Nginx 对话，其实 Nginx 背后转给了真正的应用 |
| CI/CD | 持续集成/持续部署：代码一提交，自动跑测试、自动发布 |
| 环境变量 | 给程序传配置的通道，避免把数据库密码写死在代码里 |

## 3. 分步实战

### 步骤 1：后端配置外置（上线前提）

上线前必须把环境差异从代码里剥出来：

> **提示词示例：**
>
> ```
> 为 qshop-server 做生产配置分离：
> 1. application-prod.yml：数据库/Redis 地址、JWT 密钥全部用环境变量占位（${DB_PASSWORD} 等）
> 2. 检查代码中没有任何硬编码的密码、密钥、本机路径（upload 目录改为可配置）
> 3. Swagger 在 prod 禁用
> ```

**检查要点**：全局搜索 `password`、`secret` 关键字逐一确认——**任何出现在 Git 里的真实密码都是事故**。

### 步骤 2：后端 Docker 化

> **提示词示例：**
>
> ```
> 为 qshop-server 编写多阶段 Dockerfile：
> 阶段 1 用 Maven 镜像构建 jar；阶段 2 用 JDK 17 精简镜像运行，
> 暴露 8080，通过环境变量注入 SPRING_PROFILES_ACTIVE=prod 与数据库配置。
> 给我构建和运行的完整命令。
> ```

**预期产出**：`Dockerfile` + 构建运行命令。

**验证**（需本机 Docker）：

```powershell
docker build -t qshop-server .
docker run -p 8080:8080 -e DB_PASSWORD=xxx qshop-server
```

访问 `http://localhost:8080/api/v1/products` 返回数据即成功。

> 没有 Docker 环境？让 AI 讲解 Dockerfile 每一行含义并记录，作为理解性学习，不影响结业。

**检查要点**：镜像里有没有把源码、测试代码、开发配置打进去（多阶段构建的意义正是甩掉它们）。

### 步骤 3：Nginx 生产架构

> **提示词示例：**
>
> ```
> 请给出 QShop 的 Nginx 生产配置并讲解：
> 1. 前端静态资源（qshop-web 的 npm run build 产物）由 Nginx 直接服务
> 2. /api/ 与 /files/ 反向代理到后端 8080
> 3. SPA 路由支持（try_files 回退 index.html）
> 4. 解释为什么这种部署方式天然解决 CORS
> ```

**预期产出**：`nginx.conf` 示例 + 架构图。

**关键理解**：同源部署下，浏览器看到的页面和接口来自同一个域名，跨域问题从根上消失——这就是第 13 讲「生产用 Nginx 同源」的落地。

### 步骤 4：CI/CD 思路（理解为主）

> **提示词示例：**
>
> ```
> 请为 QShop 设计一条最小 CI/CD 流水线（以 GitHub Actions 为例，讲解为主不必真实配置）：
> push 触发 → 编译 + 运行单元测试（含并发回归测试）→ 构建 Docker 镜像 → 部署。
> 讲清每一步在防什么风险。
> ```

**要点体会**：CI/CD 的本质是把「每次提交都重复一次完整质检」自动化。第 14 讲固化的并发回归测试，正是这条流水线上最有价值的守门员。

### 步骤 5：用热门 Skill 部署前端演示站

体验「Skills 把固定流程产品化」的价值：

> **操作指引**：在 Qoder 对话中发起前端部署（例如使用 vercel-deploy 技能），按 Skill 的引导完成 qshop-web 的构建与部署，获得一个公网可访问的演示地址。

**观察与思考**：

1. Skill 引导你做了哪些步骤？（装 CLI → 登录 → 构建 → 上传 → 出地址）这些步骤和你自己摸索相比快多少？
2. 部署的前端演示站接口指向哪里？（注意：纯静态部署没有同源后端，接口会失败——这正好反过来印证 Nginx 同源架构的意义。把这一点写进笔记）

## 4. 常见坑

1. **容器内连不上本机数据库**：容器里的 `localhost` 指容器自己。连宿主机 MySQL 要用 `host.docker.internal`（Windows/Mac）或宿主机 IP。
2. **环境变量没生效**：配置类用了 `${DB_PASSWORD}` 但没给默认值时，变量缺失会直接启动失败——这正是我们要的「宁可启动失败，不可用错配置」。
3. **前端 build 后接口路径错误**：检查 baseURL 是否用了相对路径 `/api/v1`，以及部署平台的路由回退配置。

1. 为项目编写 README：项目介绍、技术栈、本地运行步骤、部署方式——让 AI 起草、你审校

## 6. 进阶路线

| 方向 | 什么时候学 | 入口 |
| --- | --- | --- |
| 自建 MCP Server | 当你需要 AI 连接内部系统（数据库、工单、监控）时 | MCP 官方规范 + Qoder MCP 配置 |
| 自定义 Skills | 当某个流程你重复教了 AI 三遍以上 | create-skill 技能引导 |
| 多子 Agent 协作 | 当单对话上下文太长、任务可明确分工时 | 子 Agent 编排实践 |
| Spec Kit 生态 | 当团队要定制流程时 | Preset / Extension / Workflow |
| 高并发库存与削峰方案 | 当乐观锁 + 单体数据库真的成为瓶颈时 | Redis 预扣减、分段库存、消息队列削峰 |
| 微服务改造 | 当单体真的撑不住时（而不是为了简历） | 先学服务拆分原则再动手 |
