# 第 03 讲 · Spec 驱动开发与 OpenSpec 实战

> 本讲是全课程最重要的方法论一讲：学会「先写清楚要什么，再让 AI 动手」。我们将使用开源轻量工具 OpenSpec 完成第一次完整的 Spec 驱动开发演练。

## 1. 学习目标与本讲地图

学完本讲，你将能够：

- [ ] 解释为什么「一句话需求直接让 AI 写代码」会翻车
- [ ] 说出 Spec 驱动开发（SDD）的核心理念
- [ ] 安装并初始化 OpenSpec
- [ ] 知道 /opsx:explore 的定位：需求不清时先「零成本思考」
- [ ] 完整走一遍 propose（提案）→ apply（实现）→ sync（合并）→ archive（归档）流程
- [ ] 看懂每个阶段产出的 Markdown 工件的作用，理解「增量规格（delta）」
- [ ] 了解 Qoder Plan Mode 与 OpenSpec 的关系（轻量补充）

本讲地图：

```
翻车案例 → SDD 理念 → 安装 OpenSpec → 探索与提案 → 实现与归档 → 质量检查 → Plan Mode 对比
```

## 2. 术语表

| 术语 | 一句话理解 |
| --- | --- |
| Spec（规格/规格书） | 用文档把「系统必须表现出什么行为」写清楚，是行为契约而不是实现细节 |
| SDD（Spec-Driven Development，Spec 驱动开发） | 先写规格、再写代码的开发流程 |
| OpenSpec | 开源轻量的 SDD 框架：只管理规格文件本身，生成和实现交给你的 AI 助手 |
| proposal（提案） | 一次变更的完整提案：意图与范围（proposal.md）+ 设计（design.md）+ 任务清单（tasks.md）+ 增量规格 |
| delta（增量规格） | 只描述「这次改了什么」的规格片段，分 ADDED / MODIFIED / REMOVED 三类 |
| specs（主规格） | 系统当前行为的「真相源」，按功能域存放，随变更不断生长 |
| archive（归档） | 变更完成后把它移入历史目录，变更内容合并进主规格 |
| AGENTS.md | 「写给 AI 看的 README」：告诉 AI 如何读规格、如何走流程 |
| Plan Mode（计划模式） | Qoder 内置功能：AI 先出实施方案，你确认后才动手改代码 |

## 3. 为什么需要 Spec 驱动开发：一个翻车案例

假设你对 AI 说：

> 「帮我写一个电商网站的购物车功能。」

AI 会立刻开始写代码。但它不得不自己猜：

- 购物车存数据库还是 Redis？
- 游客能不能加购？
- 商品下架了购物车里怎么处理？
- 数量上限多少？价格为 0 的赠品怎么算？

每个它猜的地方，都是未来返工的地方。更糟的是：**代码已经写了一大堆，你想改方向只能推翻重来**。这就是「vibe coding（凭感觉写代码）」的典型结局——小玩具没问题，企业级项目必翻车。

**SDD 的解法**：把「猜」的环节前置成「写清楚」。在写代码之前，先用结构化文档锁定需求、方案和任务。文档一旦确定，AI 每次实现都有据可依，你审查也有据可查。

**一句话记忆：代码是最贵的产出，所以要让最便宜的产出（文档）先跑在前面。**

### 为什么本课程选 OpenSpec

市面 SDD 工具不少，OpenSpec 胜在「轻」：

- **零依赖**：不需要 API Key、不需要 MCP，装一个 npm 包就能用，规格就是仓库里的纯 Markdown 文件
- **流程短**：核心只有「提案 → 实现 → 归档」几步，没有冗长的多阶段仪式
- **增量规格（delta）**：每次变更只写「改了哪几条行为」，合并进主规格后，项目文档随代码一起生长，而不是烂尾成一堆过时计划
- **不限 AI 工具**：它只负责管理规格文件，生成工作由你正在用的 AI（Qoder）完成；即使工具没有原生集成，也能靠读取 AGENTS.md 跟上流程

## 4. Qoder 能力点讲解

## 5. 安装 OpenSpec

### 5.1 前置条件

- Node.js 20.19+（验证：`node -v`；第 11 讲前端部分同样需要它）

### 5.2 全局安装 CLI

```powershell
npm install -g @fission-ai/openspec@latest
```

验证：

```powershell
openspec --version
```

> 提示：若提示命令不存在，关闭并重开终端，让 PATH 生效。

### 5.3 初始化演练项目

本讲用一个小型演练项目走完整流程：**命令行待办清单（Todo CLI）**——麻雀虽小五脏俱全。

```powershell
mkdir openspec-demo
cd openspec-demo
openspec init
```

初始化会交互式询问你的 AI 工具。列表中有 Qoder 就直接选；**没有就选 Generic**——它会生成通用的 AGENTS.md 指引，Qoder 读取后照样能完整遵循流程。

初始化成功后，你会看到类似结构：

```
openspec-demo/
└── openspec/
    ├── project.md         # 项目背景与约定（相当于项目「宪法」的位置）
    ├── AGENTS.md          # 写给 AI 的流程说明书
    ├── specs/             # 主规格：系统当前行为的真相源（初始为空）
    └── changes/           # 变更提案区，每个变更一个文件夹
        └── archive/       # 已完成变更的归档
```

**开工前先做一件事**：打开 `openspec/project.md`，把项目原则写进去（OpenSpec 没有独立的「宪法」命令，project.md 就是承载项目底线的地方）：

```markdown
# Todo CLI 项目约定
- Python 3.11+，不引入 Web 框架，只做命令行工具
- 数据持久化用本地 JSON 文件，不引入数据库
- 所有对外函数必须有单元测试
- 代码注释与文档使用中文
```

## 6. 实战演练：Todo CLI 的完整流程

> 命令名提示：`/opsx:propose` 是标准写法，但不同 AI 工具的拼写可能略有差异（如 Cursor/GitHub Copilot 里是 `/opsx-propose`，Codex 里是 `$openspec-propose`）。`openspec init` 完成后会打印你所选工具对应的命令形式，以它为准。
>
> 官方使用建议：进入 apply 实现阶段前**先清理对话上下文**（呼应第 02 讲的「何时开新会话」）——把提案文档 @ 给新会话，比拖着长长的规划历史开工效果更好。

### 阶段 0（可选）：explore——需求不清时先探索

如果你还不确定要做什么、怎么做，不必硬写提案。OpenSpec 默认流程提供了「零风险思考伙伴」：

> **指令示例：**
>
> ```
> /opsx:explore 我想给待办清单加一个提醒功能，但不确定命令行工具怎么做提醒才合理，帮我分析几种方案。
> ```

explore 不生成任何文档、不写代码，只是一场有代码库上下文的方案讨论；想清楚后再进入 propose。本讲演练需求已很明确，可直接跳过此阶段——但在 QShop 这样真实项目里，它是需求澄清的好帮手。

### 阶段 1：propose——一次性生成完整提案

在 AI 对话中输入：

> **指令示例：**
>
> ```
> /opsx:propose 为 Todo CLI 增加"命令行待办清单"功能：
> 1. 作为用户，我可以添加待办事项（带标题，可选截止日期）
> 2. 作为用户，我可以查看待办列表，区分"未完成/已完成/已过期"
> 3. 作为用户，我可以把某个待办标记为完成，并记录完成时间
> 4. 作为用户，我可以删除待办事项
> 5. 作为用户，我可以按截止日期或创建时间排序
> 技术约束：Python 3.11+ 标准库为主，参数解析用 argparse，数据存 data/todos.json。
> ```

**预期产出**：`openspec/changes/<变更名>/` 目录，内含：

| 文件 | 作用 |
| --- | --- |
| `proposal.md` | 意图与范围：为什么做、做什么、不做什么 |
| `design.md` | 技术设计：数据结构、模块划分 |
| `tasks.md` | 任务清单：可逐个实现和验证的小步骤 |
| `specs/.../spec.md` | **增量规格（delta）**：这次变更涉及的行为要求 |

**检查要点（本阶段是质量的关键）**：

- 逐条对照你的原始需求，看 proposal 有没有漏项或被曲解
- 重点看 delta 规格里的行为要求（形如「MUST/SHOULD」的条款 + Given/When/Then 场景），这些「被提前写出来的边界」正是 SDD 的价值所在——例如标题为空怎么办？截止日期已过还能标记完成吗？
- 不满意就直接让 AI 改：「proposal.md 补充：标记完成时记录完成时间」
- **确认满意前，不要进入下一步**——改文档比改代码便宜得多

> 小插曲：如果 AI 不认识 `/opsx:propose` 命令（Generic 集成时可能发生），先确认是不是上面提到的拼写差异问题；还不行就把指令改成自然语言：「请先阅读 @openspec/AGENTS.md，然后按 OpenSpec 流程为下面的需求创建变更提案：……」——效果相同。

### 阶段 2：apply——逐任务实现

> **指令示例（先只做第一个任务）：**
>
> ```
> /opsx:apply 请按 tasks.md 实现第一个任务。
> ```

**预期产出**：AI 按 tasks.md 的描述生成代码，并把该任务在清单中标记完成。

**工作节奏（本讲最重要的习惯）**：

1. **一次只做一个任务**，做完运行验证（`python todo.py add "学习 OpenSpec"`）通过后再做下一个
2. 发现实现与规格不符时，先判断：是代码错了（改代码），还是规格想错了（改规格再改代码）
3. 全部任务完成后，对照 delta 规格里的行为要求逐条验收

### 阶段 3：sync + archive——合并与归档

功能验证通过后：

> **指令示例：**
>
> ```
> /opsx:archive 功能已完成并验证，请归档这次变更。
> ```

**预期产出**：

- delta 规格合并进 `openspec/specs/`（主规格从此拥有「待办清单」这个功能域的行为契约）
- 变更目录移入 `changes/archive/`（带日期前缀，成为可追溯的历史）

**检查要点**：打开 `openspec/specs/` 确认合并后的主规格完整可读——**这就是「文档随项目生长」的直观体现**。下一个功能提案时，AI 会先读主规格了解系统现状，避免破坏已有行为。

至此，你完整走完了一次 Spec 驱动开发闭环：

```
propose（提案）→ apply（实现）→ sync/archive（合并归档）
  做什么+怎么做+分成几步    一步步做        沉淀进主规格
```

### 两个质量检查命令（按需使用）

| 命令 | 作用 | 何时用 |
| --- | --- | --- |
| `openspec validate` | 检查规格文件结构是否完整合规（只查结构，不查行为对错） | 提案生成后、归档前 |
| `/opsx:verify` | 检查实现的完整度与一致性（建议性质，不阻止归档） | apply 之后，归档之前顺手跑一次 |

> 注意：`/opsx:verify` 属于扩展命令集，默认 profile 里可能没有。需要时执行 `openspec config profile` 选择扩展工作流，再用 `openspec update` 刷新命令；升级 OpenSpec 版本后也建议跑一次 `openspec update` 保持命令与指引最新。

> 提醒：OpenSpec 的检查都是「提醒」而非「强制门禁」——规格写得对不对、实现有没有偏离，最终靠你审查。这也是它「轻」的代价，第 8 讲常见坑会再提。

## 7. Qoder Plan Mode：轻量版的「先方案后施工」

OpenSpec 适合完整功能的正式流程；日常小改动不必每次都提案归档。Qoder 的 Plan Mode 是轻量补充：

- 开启 Plan Mode 后，AI **只出实施方案、不动代码**
- 你审查方案、提出修改，确认后才开始施工
- 适合「改一个功能」「重构一个类」这类中等规模任务

**选择建议**：

| 场景 | 用什么 |
| --- | --- |
| 新功能模块、跨多文件的复杂改动 | OpenSpec 完整流程 |
| 单点功能修改、小重构 | Plan Mode |
| 改个文案、修个明显小 bug | 直接对话 |

> **练习**：切到 Plan Mode，对演练项目提一个需求「增加 /stats 命令，统计各状态待办数量」，观察 AI 先出方案、待你确认的流程。

## 8. 常见坑与 AI 幻觉识别

1. **AI 生成的提案比你想象的「详细」，但可能是编的**。提案里出现的每个业务规则，都要问自己：这是我想要的，还是 AI 脑补的？例如 AI 可能自行规定「待办标题最长 50 字」——可以接受，但要过目。
2. **design 阶段偷偷违反 project.md 约定**。例如 AI 提议引入 SQLite 就违反项目约定，必须驳回。审查提案时对照 project.md 逐条过。
3. **任务粒度过大**。如果某个 task 描述超过 5 行，让 AI 继续拆分。
4. **apply 时脱离规格自由发挥**。发现 AI 实现了规格里没有的功能，要求它删除——范围蔓延是企业项目失控的常见原因。
5. **规格漂移（drift）**：OpenSpec 不强制代码与规格同步，AI 实现时偷偷改了行为，规格不会自动更新。对策：apply 阶段逐任务对照规格验收；怀疑漂移时用 `/opsx:verify` 检查一致性。
6. **跳过 sync 直接归档**。归档不合并主规格，下个变更的 AI 就读不到系统现状，「防止破坏已有功能」的机制就失效了。归档时留意是否提示先 sync。

## 9. 课后练习任务

1. 继续完成 Todo CLI 的剩余任务，体验「逐任务实现 + 逐任务验证」的节奏，完成后走完 sync + archive
2. 中途故意修改一次需求（例如给 add 命令加优先级参数）：直接对 AI 说「修改当前变更的 proposal 与 delta 规格：……」，体会「文档先行」的修改流程——感受 delta 只改增量、不动全局的便利
3. 用 Plan Mode 完成一个小功能，对比它与 OpenSpec 流程的轻重差异
4. 写下你的体会：OpenSpec 四步中，哪一步的产出对代码质量影响最大？参考答案：propose 阶段——需求错了，后面设计、任务、代码全部跟着错，而且越晚发现返工成本越高；这正是「代码最贵、文档先行」的原因
