# 第 10 讲 · 支付、库存与并发

> 本讲处理电商最难的两件事：钱（支付链路）和并发（库存超卖）。你将学会如何向 AI 准确描述并发约束，并验证它的方案真的有效。

## 1. 学习目标与本讲地图

学完本讲，你将能够：

- [ ] 解释「超卖」是怎么发生的（用时间线推演）
- [ ] 实现乐观锁防超卖，并用并发测试证明它有效
- [ ] 实现模拟支付与支付回调，完成订单状态流转闭环
- [ ] 说清「支付回调」为什么要幂等
- [ ] 掌握「向 AI 描述并发约束」的提示词方法

本讲地图：

```
超卖原理 → 乐观锁方案 → 并发验证 → 模拟支付 → 幂等回调 → 交易闭环验收
```

## 2. 术语表

| 术语 | 一句话理解 |
| --- | --- |
| 超卖 | 库存只有 1 件，两个人同时下单都成功了——卖出了不存在的货 |
| 并发 | 多个请求同一瞬间挤进来，抢同一份数据 |
| 乐观锁 | 假设冲突很少发生，更新时核对「版本号」，被人改过就失败重试 |
| version 字段 | 乐观锁的载体：每次更新 +1，更新条件带上旧值 |
| 幂等 | 同一操作执行一次和执行多次，结果完全相同 |
| 支付回调 | 支付渠道通知你「这笔钱收到了」的接口；课程中由模拟页触发 |

## 3. 企业级知识点

### 3.1 超卖是怎么发生的

库存=1，两个请求几乎同时到达：

```
时刻  请求A                    请求B
t1   查库存 = 1 ✓
t2                            查库存 = 1 ✓
t3   扣减 → 库存 = 0
t4                            扣减 → 库存 = -1  ← 超卖！
```

「查」和「扣」之间没有原子性保证，就有并发窗口。**让 AI 写并发代码前，自己先能画出这张时间线图**——你画不出来，就说明还没法判断 AI 的方案对不对。

### 3.2 乐观锁方案（本课程选型）

给 product 表加 `version INT`：

```sql
UPDATE product SET stock = stock - #{qty}, version = version + 1
WHERE id = #{id} AND version = #{oldVersion} AND stock >= #{qty}
```

- 影响行数 = 0 → 说明版本变了或库存不够 → 抛「库存不足」（错误码 10001）
- 课程单机场景下乐观锁足够；真实高并发场景还有 Redis 预扣、分段库存等进阶方案（第 16 讲进阶路线提及）

### 3.3 支付回调为什么要幂等

真实支付渠道可能因网络重试**重复调用回调**。如果回调处理不做幂等，同一笔订单可能被重复记账。实现方式：回调先查 payment 记录，已成功处理的直接返回成功，不再重复执行状态流转。

## 4. 分步实战

### 步骤 1：模块提案

> **提示词示例：**
>
> ```
> /opsx:propose 为 QShop 创建「支付与库存」模块变更提案（含规格、设计与任务）：
> 库存：下单时校验并扣减库存（乐观锁），失败返回错误码 10001 且订单整体回滚；取消订单时回补库存
> 支付：模拟支付——创建支付单（payment 表，payment_no 前缀 P）；提供"模拟支付成功"接口模拟渠道回调；
> 回调幂等：重复调用不产生副作用；支付成功后订单 UNPAID→PAID、商品销量累加
> 明确并发约束：同一商品并发下单不得超卖（这是验收标准）
> ```

**检查要点**：「并发下单不得超卖」必须出现在 delta 规格的行为要求里——它是本讲的测试靶子。

### 步骤 2：表结构变更 + 乐观锁配置

> **提示词示例：**
>
> ```
> 1. 生成 ALTER 语句：product 表增加 version INT NOT NULL DEFAULT 0（同步更新 schema.sql）
> 2. Product 实体的 version 字段加 MyBatis-Plus @Version 注解
> 3. MybatisPlusConfig 注册 OptimisticLockerInnerInterceptor
> 4. 实现库存扣减方法：带 stock >= 数量的更新条件，失败抛 BusinessException(STOCK_NOT_ENOUGH)
> ```

**预期产出**：迁移 SQL + 实体注解 + 插件注册 + 扣减逻辑。

**检查要点**：

- 扣减必须**同时带库存条件**（`stock >= qty`）——只靠 version 防不了「库存充足但数量不够」的场景
- 迁移脚本已实际执行到数据库（`DESC product;` 验证）

### 步骤 3：并发验证（本讲核心技能：证明方案有效）

不要相信「理论上没问题」，让 AI 写并发测试：

> **提示词示例：**
>
> ```
> 写一个并发测试：把某商品库存重置为 10，用 20 个线程同时下单（每个买 1 件），
> 断言最终成功订单数 = 10、失败数 = 10、数据库库存 = 0（不为负数）。
> ```

**预期产出**：测试代码（JUnit 并发测试或临时 main 方法均可）。

**验证流程**：

1. 先运行**没加乐观锁的旧逻辑**（可临时注释 version 条件）→ 大概率复现超卖（库存为负）
2. 再运行乐观锁版本 → 成功数恒等于 10

这个「先复现问题，再验证修复」的流程，是并发问题的标准验证方法。**如果 AI 的方案没法通过并发测试，把测试失败结果贴回给它迭代**——测试即提示词。

### 步骤 4：模拟支付链路

> **提示词示例：**
>
> ```
> @openspec/changes（引用支付与库存变更目录的提案与 delta 规格）实现模拟支付：
> 1. POST /api/v1/payments：对 UNPAID 订单创建支付单，返回 payment_no 与"模拟支付页"信息
> 2. POST /api/v1/payments/{paymentNo}/mock-callback：模拟渠道回调"支付成功"，
>    入参带幂等键（可用 paymentNo 本身）
> 3. 回调处理（@Transactional）：幂等检查 → 更新支付单 PAID → 订单 UNPAID→PAID → 商品销量累加
> 4. 重复调用回调：第二次起直接返回成功，不重复流转
> ```

**预期产出**：`modules/payment/` 代码。

**验证（完整交易闭环）**：

下单 → 创建支付单 → 模拟回调 → 订单变 PAID → 再次回调确认幂等（订单状态不变、无重复记录）→ 用 SQL 核对 payment/order/product 三表数据一致。

**检查要点**：

- 回调里的状态流转是否复用了第 09 讲的状态机组件（而不是新写一套 if）
- 「订单已支付时再次回调」与「支付单不存在」两种情况的返回是否都合理

## 5. 常见坑与 AI 幻觉识别

1. **假乐观锁**：AI 可能只加了 `@Version` 注解却没注册拦截器，或更新时没走 MyBatis-Plus 的 updateById——version 条件不会生效。**用并发测试证伪，别用眼睛看。**
2. **先查后改的伪并发方案**：`if (stock >= qty) { stock--; update; }` 这种代码在并发下必超卖，看到就驳回，要求改成条件更新。
3. **回调不做幂等**：检查重复回调是否会产生第二条流转记录或重复加销量。
4. **事务范围错误**：回调里「改支付单 + 改订单 + 加销量」必须在同一事务。
5. **取消订单不回补库存**：对照提案的 delta 规格检查回补逻辑存在且数值正确。
