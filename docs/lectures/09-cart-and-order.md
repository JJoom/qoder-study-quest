# 第 09 讲 · 购物车与订单

> 本讲进入电商核心交易链路：Redis 购物车 + 下单与订单状态机。你将学会如何用 AI 辅助设计「状态流转」这类业务规则密集型功能。

## 1. 学习目标与本讲地图

学完本讲，你将能够：

- [ ] 说清购物车为什么适合存 Redis 而不是数据库
- [ ] 实现加购、改数量、删除、查询购物车接口
- [ ] 解释订单状态机：每个状态能做什么、不能做什么
- [ ] 实现下单接口（地址快照、商品快照、状态初始化为 UNPAID）
- [ ] 实现收货地址管理接口（归属校验的越权防线首战）
- [ ] 用「先画状态图再写代码」的方式让 AI 实现状态流转校验

本讲地图：

```
购物车方案 → 购物车接口 → 订单状态机设计 → 下单实现 → 地址管理 → 订单查询与取消
```

## 2. 术语表

| 术语 | 一句话理解 |
| --- | --- |
| Redis Hash | Redis 的一种数据结构：一个 key 下挂多组 field-value，适合存「某用户的购物车」 |
| 订单号 | 订单的唯一业务编号，对外展示用，与自增主键分离 |
| 状态机 | 一组状态 + 合法流转规则，例如「待支付 → 已支付」合法，「已取消 → 已支付」非法 |
| 快照 | 下单瞬间把地址、商品信息复制进订单，之后原始数据变更不影响历史订单 |

## 3. 企业级知识点

### 3.1 购物车为什么存 Redis

购物车特点：**读多写多、允许丢失（重建成本低）、按用户隔离、不需要事务**。这正是 Redis Hash 的理想场景：

```
key:   cart:user:{userId}
field: {productId}
value: {数量, 加入时间}
```

查询时再用 productId 批量回查商品表拿最新价格（价格必须实时，不能用加购时的旧价——商品改价了购物车要跟着变）。

### 3.2 订单状态机先画再写

课程订单状态（见项目规格书第 6 节）：

```
UNPAID ──支付成功──> PAID
UNPAID ──取消────> CANCELLED
PAID   ──退款────> REFUNDED
```

**设计方法**：列出「状态 × 动作」矩阵，哪些组合合法一目了然：

| 动作 \ 当前状态 | UNPAID | PAID | CANCELLED | REFUNDED |
| --- | --- | --- | --- | --- |
| 支付 | 合法 | 拒绝（10002） | 拒绝 | 拒绝 |
| 取消 | 合法 | 拒绝 | 拒绝 | 拒绝 |
| 退款 | 拒绝 | 合法 | 拒绝 | 拒绝 |

让 AI 写代码前先把这张表放进 spec——状态类 bug 大多源于「没有先定义合法流转」。

## 4. 分步实战

> 前置：确保本地 Redis 已启动（`redis-cli ping` 返回 PONG）。

### 步骤 1：模块 Spec

> **提示词示例：**
>
> ```
> /speckit.specify 为 QShop 编写「购物车与订单」模块规格：
> 购物车（Redis 存储）：加购（同一商品累加数量）、修改数量（最小 1）、删除、查询（含商品最新价格与库存状态）；购物车数据与登录用户绑定
> 订单：从购物车勾选商品下单 → 生成订单号、地址快照、商品快照、总金额，状态 UNPAID；下单后从购物车移除已购商品
> 订单查询：我的订单列表（分页+按状态筛选）、订单详情（仅本人可见）
> 订单取消：仅 UNPAID 可取消（错误码 10002 用于非法流转）
> 本讲不处理库存扣减与支付（第 10 讲），下单逻辑预留库存校验接入点
> ```

**检查要点**：确认「订单详情仅本人可见」写进了验收标准——越权查看他人订单是电商高频漏洞。

### 步骤 2：购物车接口

> **提示词示例：**
>
> ```
> @specs/004-cart-order/spec.md @modules/category
> 实现购物车模块 modules/cart（参照样板风格，Redis 用 Spring Data Redis 的 StringRedisTemplate）：
> 1. POST /api/v1/cart/items：加购 {productId, quantity}，校验商品存在且上架，数量上限 99
> 2. PUT /api/v1/cart/items/{productId}：修改数量
> 3. DELETE /api/v1/cart/items/{productId}：删除单项
> 4. GET /api/v1/cart：返回购物车列表，每项含商品最新名称/价格/图片/库存/上架状态
> Redis key 设计：cart:user:{userId}，field=productId，value 存 JSON（数量+加入时间）
> ```

**预期产出**：`modules/cart/` 代码。

**验证**：登录后加购两个商品 → 查询购物车 → 用 `redis-cli HGETALL cart:user:2` 查看原始数据与代码设计一致。

**检查要点**：

- userId 必须从 JWT 认证上下文取，**绝不能信任前端传来的 userId**（越权红线）
- 商品价格是否实时回查商品表，而不是存在购物车里

### 步骤 3：下单接口

> **提示词示例：**
>
> ```
> 实现下单接口 POST /api/v1/orders，入参 {addressId, productIds[]}：
> 1. 校验地址属于当前用户；校验所选商品均在购物车、均上架
> 2. 生成订单号（yyyyMMddHHmmss + 6位随机数）
> 3. 写 order 主表：地址快照字段、总金额（用 BigDecimal 逐项累加）；写 order_item：商品快照（名称/图片/单价/数量）
> 4. 状态 UNPAID；成功后从购物车移除已购商品
> 5. 整个方法加 @Transactional，任何一步失败全部回滚
> 6. 预留注释：库存校验与扣减在第 10 讲接入
> ```

**预期产出**：`modules/order/` 下单链路代码。

**验证**：下单成功 → 数据库出现 order + order_item 记录 → 购物车中对应商品消失 → 故意传他人地址 id，确认被拒绝。

**检查要点（重点）**：

- `@Transactional` 在 Service 实现类的 public 方法上（private 方法上无效——高频坑）
- 总金额是服务端用「单价 × 数量」重新计算的，**绝不能信任前端传来的总价**
- 订单号唯一性冲突时的处理（重试或报错），而不是静默吞掉

### 步骤 4：地址管理接口（下单的前置条件）

下单需要 addressId，但用户此时还没有任何创建地址的途径——先把地址模块补上。这也是第 06 讲样板模块的一次完整复制练习：

> **提示词示例：**
>
> ```
> @db/schema.sql @modules/category 参照样板风格实现地址模块 modules/address（均需登录）：
> 1. GET /api/v1/addresses：当前用户的地址列表
> 2. POST /api/v1/addresses：新增地址（收件人、手机号、省市区、详细地址、是否默认）
> 3. PUT /api/v1/addresses/{id} 修改、DELETE /api/v1/addresses/{id} 删除，均须校验地址属于当前用户
> 4. PUT /api/v1/addresses/{id}/default 设为默认（先取消原默认，保证唯一）
> 5. userId 一律从认证上下文获取，禁止信任入参
> ```

**预期产出**：`modules/address/` 全套代码。

**验证**：新增地址 → 查询列表 → 设默认 → 再用另一个账号的地址 id 调修改接口，确认被拒绝。

**检查要点**：修改/删除/设默认是否都带归属校验——这是步骤 3「越权红线」的第一次落地，第 15 讲安全排查还会专门复测它。

### 步骤 5：订单查询与取消（状态机落地）

> **提示词示例：**
>
> ```
> 1. GET /api/v1/orders：我的订单分页列表，参数 page/size/status
> 2. GET /api/v1/orders/{orderNo}：详情，订单不属于当前用户返回 404（不要返回 403，避免暴露订单存在性）
> 3. PUT /api/v1/orders/{orderNo}/cancel：取消订单
> 按 spec 中的"状态×动作"矩阵实现流转校验，非法流转抛 BusinessException(ORDER_STATUS_INVALID)，
> 用枚举 + 状态流转方法集中管理规则，不要把 if 判断散落各处。
> ```

**预期产出**：订单查询与取消接口 + 集中的状态流转逻辑。

**验证**：下单 → 取消成功 → 再次取消同订单，确认返回 10002。

**检查要点**：状态流转规则是否集中在一处（枚举或状态机组件）。如果 AI 把判断散在 Controller 和多个 Service 里，要求重构——规则散落是状态 bug 的温床。

## 5. 常见坑与 AI 幻觉识别

1. **越权三连**（本讲最危险的一类错误）：userId 来自前端参数、订单详情不校验归属、地址不校验归属。逐个接口检查「资源归属校验」。
2. **金额用 double**：搜索代码中的 `double`/`float` 与金额运算。
3. **事务注解位置错误**：`@Transactional` 写在接口上、private 方法上、或被自调用绕过（同类内部 this 调用不走代理）都会失效。
4. **Redis 操作幻觉**：AI 可能用错 API（如 `opsForValue` 存 Hash 结构）。用 `redis-cli` 看真实存储结构验证。
5. **状态机漏边界**：让 AI 自查「列出所有状态 × 动作组合及处理结果」，对照你的矩阵核对。
